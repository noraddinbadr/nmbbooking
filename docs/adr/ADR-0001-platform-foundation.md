# ADR-0001: تأسيس منصة مواقع أعمال ديناميكية متعددة العملاء

**الحالة:** معتمد
**التاريخ:** 2026-08-15
**صاحب القرار:** مالك المنتج وفريق الهندسة

## السياق

المنتج منصة SaaS ديناميكية لإنشاء وتشغيل مواقع شركات متعددة القطاعات واللغات. تتطلب المنصة رندرًا عامًا من الخادم لكل طلب، تحرير صفحات قائمًا على الإصدارات والبلوكات، حزمًا قابلة للتفعيل، لوحة إدارة مركزية واحدة، عزلًا قويًا لبيانات العملاء، وقابلية تشغيل أولية على Namecheap Shared Hosting لعدد محدود من العملاء ثم انتقالًا منظّمًا إلى VPS أو Dedicated عند الحاجة.

## القرار

يعتمد المنتج على **Laravel/PHP** كتطبيق خادم موحد. تُرندر المواقع العامة ديناميكيًا عبر Blade، وتُبنى لوحة التحكم الواحدة فوق Laravel باستخدام Backpack، مع بقاء workflows في طبقة Application لا في أداة اللوحة. تستهلك تطبيقات iOS وAndroid، المبنية بـ Expo/React Native، واجهة Laravel API المصدّرة بالعقود المحددة.

يعتمد تعدد العملاء على:

```text
platform_core MySQL مع جداول InnoDB
  → users, tenants, memberships, plans, entitlements, addresses, tenant DB registry

tenant_<slug> MySQL مع جداول InnoDB
  → sites, pages, revisions, blocks, translations, media, forms, activations, sector data
```

تكون هوية المستخدم مركزية في `platform_core`. لا تُنسخ الحسابات أو كلمات المرور إلى قواعد العملاء. تُنشر الحزم ضمن application release، بينما يغيّر تفعيلها state/config في قاعدة العميل فقط. لا تُنفذ migrations أو Composer أو تنزيل كود عند تفعيل حزمة.

## البدائل المرفوضة

| البديل | سبب الرفض |
|---|---|
| توليد صفحات HTML ثابتة | يتعارض مع مطلب الرندر الديناميكي الكامل وإصدارات المحتوى والحزم الحية. |
| قاعدة بيانات موحدة بكل العملاء | لا تتفق مع قرار العزل المادي الملائم لحجم 20–30 عميلًا في المرحلة الأولى. |
| SQLite كمصدر حقيقة | غير مناسب لمنصة SaaS متعددة العملاء والكتابة المتزامنة وإدارة المحتوى. |
| Filament أو لوحات متعددة | القرار هو لوحة Laravel واحدة مخصصة فوق Backpack. |
| migrations عند تفعيل الحزمة | يخلط release lifecycle مع entitlement lifecycle ويصعّب rollback والدعم. |

## النتائج والتبعات

يتطلب القرار backend منظمًا، migrations منفصلة لـ `platform_core` وTenant schema، runner لترقية قواعد العملاء بالتتابع، provisioning قابلًا للاستئناف، وسياسات backup/restore لكل Tenant. وفي المقابل، يوفر حدودًا واضحة للعزل، انتقالًا مباشرًا إلى VPS أو Dedicated، وتجربة تشغيل متسقة للوحدات والحزم والصفحات وتطبيقات الجوال.

## معايير التحقق

- يمكن لحساب منصة حل عنوان موثق إلى Tenant DB صحيحة، ولا يستطيع أي request اختيار connection يدويًا.
- لا يمكن لمستخدم قاعدة العميل قراءة `platform_core`، ولا لمستخدم المنصة قراءة قاعدة العميل في التشغيل الأدنى الصلاحية.
- لا تتغير الصفحة العامة إلا من `published_revision_id` في قاعدة العميل الصحيحة.
- أي package manifest أو component manifest غير مطابق للعقود يرفض في CI قبل النشر.
- يستطيع Tenant جديد المرور بـ provision → migrate → seed → domain verify → smoke test بصورة قابلة للاستئناف.
