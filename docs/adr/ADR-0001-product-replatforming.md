# ADR-0001: إعادة تأطير المنتج واعتماد Laravel مع قواعد MySQL مستقلة للعملاء

**الحالة:** معتمد  
**التاريخ:** 2026-08-15  
**صاحب القرار:** مالك المنتج وفريق الهندسة

## السياق

يحتوي المستودع الحالي على تطبيق React/Vite/Supabase في نطاق صحي، بينما المنتج المعتمد هو منصة SaaS ديناميكية لمواقع الأعمال متعددة العملاء والقطاعات. يتطلب المنتج الجديد رندرًا عامًا Server-Side، نظام حزم وبلوكات وإصدارات، لوحة تحكم واحدة، قواعد بيانات مستقلة للعملاء، وقابلية تشغيل على Namecheap Shared Hosting ثم الانتقال المنظم إلى VPS أو Dedicated.

استخدام الواجهة القديمة أو Supabase كقاعدة استمرار افتراضية يخلط نطاقين مختلفين ويؤخر بناء boundaries الصحيحة للمنتج. كما أن تطبيق SPA وحده لا يحقق متطلبات رندر صفحات الشركات العامة ديناميكيًا عبر PHP/Blade ولا نموذج تشغيل قواعد MySQL المقصود.

## القرار

يعتمد المنتج الجديد على **Laravel/PHP** كخادم تطبيق موحد. تُرندر المواقع العامة ديناميكيًا عبر Blade. وتُبنى لوحة التحكم الواحدة فوق Laravel باستخدام Backpack، مع بقاء workflows في طبقة Application لا في أداة اللوحة. تستخدم تطبيقات iOS وAndroid Expo/React Native وتستهلك Laravel API بالعقود المحددة.

يعتمد تعدد العملاء على:

```text
platform_core MySQL/InnoDB
  → users, tenants, memberships, plans, entitlements, addresses, tenant DB registry

tenant_<slug> MySQL/InnoDB
  → sites, pages, revisions, blocks, translations, media, forms, activations, sector data
```

تكون هوية المستخدم مركزية في `platform_core`. لا تنسخ users أو passwords إلى قواعد العملاء. الحزم تنشر ضمن application release؛ والتفعيل يغير state/config في قاعدة العميل فقط. لا تنفذ migrations أو Composer أو تنزيل كود عند تفعيل حزمة.

## البدائل التي رُفضت

| البديل | سبب الرفض |
|---|---|
| الاستمرار على تطبيق React/Supabase الحالي | نطاق أعمال مختلف، ولا يحقق Server-Side PHP/Blade أو نموذج MySQL المعتمد |
| توليد صفحات HTML ثابتة | يتعارض مع مطلب الرندر الديناميكي الكامل وإصدارات المحتوى والحزم الحية |
| قاعدة بيانات موحدة بكل العملاء | لا تتفق مع قرار العزل المادي الملائم لحجم 20–30 عميلًا في المرحلة الأولى |
| SQLite كمصدر حقيقة | غير مناسب لمنصة SaaS متعددة العملاء والكتابة المتزامنة وإدارة المحتوى |
| Filament أو لوحات متعددة | القرار هو لوحة Laravel واحدة مخصصة فوق Backpack |
| migrations عند تفعيل الحزمة | يخلط release lifecycle مع entitlement lifecycle ويصعب rollback والدعم |

## النتائج والتبعات

يتطلب القرار بناء backend جديد منظمًا وتطبيق migrations منفصلة لـ `platform_core` وTenant schema. ويستلزم runner لترقية قواعد العملاء بالتتابع، provisioning قابلًا للاستئناف، وسياسات backup/restore لكل Tenant. لا يعني القرار حذف الشفرة القائمة فورًا؛ تحفظ في branch أو أرشيف حتى يتخذ مالك المنتج قرارًا صريحًا.

في المقابل، يوفر القرار حدودًا واضحة للعزل، انتقالًا مباشرًا إلى VPS/Dedicated، وتجربة تشغيل متسقة للوحدة والحزم والصفحات وتطبيقات الجوال.

## معايير التحقق

- يمكن لحساب منصة حل عنوان موثق إلى Tenant DB صحيحة، ولا يستطيع أي request اختيار connection يدويًا.
- لا يمكن لمستخدم قاعدة العميل قراءة `platform_core`، ولا لمستخدم المنصة قراءة قاعدة العميل في التشغيل الأدنى الصلاحية.
- لا تتغير الصفحة العامة إلا من `published_revision_id` في قاعدة العميل الصحيحة.
- أي package manifest أو component manifest غير مطابق للعقود يرفض في CI قبل النشر.
- يستطيع Tenant جديد المرور بـ provision → migrate → seed → domain verify → smoke test بصورة قابلة للاستئناف.
